This page lists every method of the client, the operation each one calls, and the value it resolves with. Use it to find the method for an operation, then follow the link to the operation's reference page for its parameters, its fields and its errors.

## Conventions

A client exposes one property per resource, such as `client.messages`, and three methods of its own. Every method follows the same rules:

- **Arguments.** Path parameters come first, then the request body or the query, then an optional [options](/sdk/configuration#per-call-options) object. The SDK URL-encodes path parameters.
- **Bodies.** A request body is sent as given. Field names are the `snake_case` names of the API: the SDK converts no name.
- **Queries.** A query value that is `undefined` or `null` is left out. Every other value is sent as a string.
- **Result.** A successful call resolves with the `data` of the response. The HTTP status, the response headers, and the `trace_id` and `request_id` of the response are not available on success. A `200` cannot be told from a `201` or a `202`.
- **No content.** A `204` response resolves with `undefined`.
- **Failure.** A failed call throws: see [Errors and retries](/sdk/errors).

## The attachments helper

`attachments.upload(file, { filename, contentType }, opts?)` does three things in one call. It registers the attachment with `POST /v1/attachments`, uploads the bytes to the URL that operation returns, then polls `GET /v1/attachments/{id}` until the attachment is `ready`. It resolves with that attachment. To send the file, pass its `id` in the `attachments` array of `messages.send`.

| Input | Rule |
| --- | --- |
| `file` | A `Blob`, an `ArrayBuffer` or a `Uint8Array`. A Node.js `Buffer` qualifies. Streams and file paths are not accepted: the whole file is in memory. Any other value throws `TypeError`. |
| `filename`, `contentType` | The file name and the content type the attachment is registered with. |
| `opts.pollIntervalMs` | The wait before each poll, in milliseconds. The default is 500. |
| `opts.maxPolls` | The maximum number of polls. The default is 60. |

`opts` also takes the [per-call options](/sdk/configuration#per-call-options). Each `upload()` call registers a new attachment, unless you pass an `idempotencyKey` that an earlier call used: the API then returns the attachment registered with that key while it is `awaiting_upload` and before its upload deadline, and `409 idempotency_terminal_state` in any other state. Pass a new key for each file.

### Polling

With the defaults the helper polls 60 times, 500 ms apart: 30 seconds of waiting, plus the time of the requests. After the last poll it throws `APIError` with status `504` and code `upload_timeout`.

iSnap confirms a finished upload on a 30-second cycle, and converts an audio file before the attachment is `ready`. The default polling, 60 polls 500 milliseconds apart, can therefore end on an upload that succeeds. Raise `pollIntervalMs` to 2,000 to 5,000 milliseconds, so that `maxPolls` polls cover at least 60 seconds.

Each poll is one API request, plus its automatic retries when it fails. Each request counts against the [request-rate limit](/errors-and-rate-limits#rate-limits), 100 requests per rolling 60 seconds. At the default interval, with no retry, the helper makes up to 2 requests per second: raising `maxPolls` alone can make up to 120 requests per minute.

A timeout does not cancel the attachment.

### Failures

| Failure | Thrown |
| --- | --- |
| The file is larger than 5,368,709,120 bytes. | `APIError`, status `413`, code `attachment_exceeds_storage_limit`, before any request. |
| The registration or a poll fails. | The error of that call, after its [automatic retries](/sdk/errors#automatic-retries). |
| The upload request is refused. | `APIError`, code `upload_failed`, with the status of the upload response. |
| The upload request fails or times out. | `APIConnectionError` |
| The attachment becomes `failed`. | `APIError`, status `422`, code `upload_failed`. |
| The attachment is not `ready` after `maxPolls` polls. | `APIError`, status `504`, code `upload_timeout`. Every status other than `ready` and `failed` keeps the polling going. |

The upload request is sent once and is not retried. It has the `timeoutMs` of the client: a large file needs a larger `timeoutMs`.

When the helper throws, it gives you no attachment id: on `upload_timeout`, and on `upload_failed` with status `422`, the id is in the text of the error message only. A refused upload carries no id. To keep the id, call `attachments.create`, upload the bytes yourself, and poll `attachments.get`. [Example: uploading an attachment](/sdk/examples/upload-attachment) shows both ways, and [Attachments](/guides/attachments) gives the limits and the retention of a file.

## Health and version

| Method | Behavior |
| --- | --- |
| `client.health()` | Resolves with `{ status, timestamp, checks }` on a `200` and on a `503`. `status` is `ok` or `degraded`. Any other status throws. The call is not retried unless you pass `maxRetries`. |
| `client.version()` | Resolves with `{ version }`, the version of the API the client talks to. |

The two operations need no credential. The client sends its key with them as with every request.

```typescript
import { ISnapClient, MIN_API_VERSION, SDK_VERSION } from '@isnap/sdk'

const client = new ISnapClient({ apiKey: process.env.ISNAP_API_KEY ?? '', maxRetries: 2 })

const health = await client.health()
if (health.status === 'degraded') {
  console.warn('The API reports a degraded state.', health.timestamp)
}

const { version } = await client.version()
console.log(`SDK ${SDK_VERSION}, API ${version}, MIN_API_VERSION ${MIN_API_VERSION}`)
```

The request and response types are generated from the OpenAPI document. Their fields are the `snake_case` fields of the API. The generated `paths` and `components` types are not exported.

TypeScript rejects a request field that is not in the API. In plain JavaScript nothing checks the field names: a misspelled field is sent as given. Nine operations refuse a field they do not define with `400 validation_failed`, and every other operation ignores it, as `POST /v1/messages` does: see [Requests](/api-reference/introduction#requests).

## Versions

| Constant | Value | Meaning |
| --- | --- | --- |
| `SDK_VERSION` | `"2.2.1"` | The version of the SDK. It is independent of the API version. |
| `MIN_API_VERSION` | `"2.24.0"` | Informational: the SDK does not check it. |

The SDK follows Semantic Versioning. It sends no API version and negotiates none: `client.version()` returns the version of the API the client talks to. [Versioning and compatibility](/api-reference/introduction#versioning-and-compatibility) gives the version scheme of the API.

## Personal data

The SDK stores nothing. It passes handles, message text and metadata through as given. Many methods return them: the message, chat, trial and lookup methods, and the webhook events. Request this data only when needed. Do not copy it into logs, tickets or other tools, and refer to a contact by an id of your own.
