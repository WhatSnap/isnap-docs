---
title: "Rotate a webhook's signing secret"
description: "Mint a new signing secret for an existing subscription. Old secret stops verifying immediately."
openapi: "POST /v1/webhooks/{id}/rotate-secret"
---

Mints a new HMAC-SHA256 signing secret for an existing subscription
and returns it in the response. The previous secret stops verifying
**immediately** — there's no overlap window.

## When to use this

- **You lost the secret.** It was only shown once at creation; iSnap
  stores a hash, so this is the only way to recover.
- **You suspect a leak.** Rotate, redeploy your verifier with the new
  secret, done.
- **Scheduled rotation policy.** Some compliance regimes mandate
  periodic credential rotation.

## Cutover plan

Because there's no overlap window, deliveries between rotation and
your verifier picking up the new secret will fail signature
verification. Two safe patterns:

**Pattern 1 — temporary deactivation:**

1. PATCH `active: false` on the subscription to pause delivery.
2. Rotate the secret.
3. Update your verifier's secret.
4. PATCH `active: true` to resume.

Events that fire while inactive are dropped (not queued). Acceptable
for low-priority events; not for `message.received` on a hot account.

**Pattern 2 — verifier reads from a hot config:**

1. Update your verifier's secret config (env var, secret manager).
2. Trigger a config reload.
3. Rotate via this endpoint.
4. The verifier picks up the new secret on the next request.

The transition window is whatever your config-reload latency is. With
a hot-reloading secret manager, it's effectively zero.

## What's in the response

A fresh `sec_…` string. **iSnap shows this once** — store it before
doing anything else.
