title: "Versioning"
description: "How iSnap versions the API, what GET /v1/version returns, how to read it from the SDK."
---

iSnap versions the API with semver. The current version is at
[`GET /v1/version`](https://api.isnap.ai/v1/version):

```json
{
  "success": true,
  "data": { "version": "1.0.0" },
  "trace_id": "tr_...",
  "request_id": "req_..."
}
```

The endpoint is **unauthenticated** — call it before bootstrapping
auth, or as a quick probe in your monitoring.

## Bump policy

| Change | Bump | Example |
|---|---|---|
| Breaking — removed endpoint, type change, removed field, required field added | MAJOR | `1.x.x → 2.0.0` |
| Additive — new endpoint, new optional field, deprecation flag added | MINOR | `1.0.x → 1.1.0` |
| No contract change — internal refactor, doc clarification | PATCH | `1.0.0 → 1.0.1` |

Removals require a 30-day deprecation window minimum (see
[Deprecation lifecycle](/concepts/deprecation-lifecycle)).

## Within a major version

Within `1.x`, the contract stays **backward-compatible**. Your
integration written against 1.0.0 keeps working against 1.5.0 — the
30-day deprecation window plus 410 Gone signals give you ample notice
before any actual removal.

This means:

- **You don't need to bump your SDK in lockstep with API MINOR bumps.**
  An older SDK on a newer backend is a supported configuration.
- **Webhook events carry an `api_version` field.** Pin against it if
  your handler depends on a specific schema.
- **A new endpoint or field never breaks you.** Your code branches on
  what it knows; unknown fields are ignored.

## When to raise your SDK's `MIN_API_VERSION`

Only when your code uses a feature that requires a specific API
version. Example: a new endpoint shipped in 1.3.0 that your
integration starts calling. Set `MIN_API_VERSION = '1.3.0'` in your
code so a deployment against an older 1.2.x backend fails loudly at
startup instead of producing 404s in production.

The SDK exposes the constant:

```ts
import { MIN_API_VERSION } from '@isnap/sdk'
```

It's reference-only today — you can read it from your code, but the
SDK does not yet auto-fetch `/v1/version` and refuse incompatible
backends. Until that runtime check lands, you can do the comparison
yourself at boot:

```ts
import { ISnapClient, MIN_API_VERSION } from '@isnap/sdk'

const isnap = new ISnapClient({ apiKey: process.env.ISNAP_API_KEY! })

const { version } = await isnap.lookup.apiVersion()
if (compareSemver(version, MIN_API_VERSION) < 0) {
  throw new Error(`iSnap backend at ${version} is below SDK floor ${MIN_API_VERSION}`)
}
```

## SDK version vs API version

The `@isnap/sdk` version is decoupled from the API version. SDK semver
tracks SDK changes (new methods, retry logic, type fixes); API semver
tracks the contract surface. A 1.5.0 SDK against a 1.2.0 backend works
as long as the SDK doesn't call endpoints introduced after 1.2.0.

## Changelog

Every contract change is logged in the [Changelog](/changelog), with
the date, the new version, and a description.
