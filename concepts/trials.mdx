Trials let a prospect test iSnap end-to-end without buying a line. They
exchange real messages against an iSnap-operated **shared pool number**,
capped by a streak counter so a single trial can't be used as a
free-tier sending channel.

This page covers the data model and the design choices behind it. For
the integration walkthrough see
[Guides → Trial onboarding](/guides/trial-onboarding).

## Per-session state

A trial isn't a property of a line — it's a session of its own,
recorded independently:

```
trials
├── id
├── pool_line_id              shared pool line iSnap operates
├── paired_handle             prospect's phone number, set at pairing
├── token                     opaque, returned to the caller at init
├── api_key_hash              the trial API key (hashed)
├── streak_counter            outbounds since last inbound
├── status                    'pairing_pending' | 'paired' | 'dormant' | 'expired'
├── max_outbound_without_inbound  the cap, set at init
├── created_at
└── ...
```

The pool line carries many trials over its lifetime; any given trial
"owns" the line for the duration of its session. The trials table
keeps streak and status per session, so two concurrent trials on the
same pool line don't conflate counters.

## The streak counter

A simple two-value gate:

- **Outbound from the trial API key:** counter += 1.
- **Inbound from the paired handle:** counter = 0.
- **Counter ≥ `max_outbound_without_inbound`:** further outbound
  returns `429 trial_outbound_streak_exceeded`.

Effects:

- A trial can't be used to blast cold messages — the second outbound
  without a reply pushes the counter, the cap stops the loop.
- Real conversations clear the counter naturally — every reply resets
  it.
- The cap is configurable per trial via `max_outbound_without_inbound`
  on `POST /v1/trial/init` (range 1–100).

## Self-echo enforcement

The trial API key is scoped to send **only** to the `paired_handle`
recorded on the trial. This is checked server-side at every send:

```
if api_key.is_trial:
  if message.to != trial.paired_handle:
    return 403 trial_self_echo_only
```

The recipient is set **at pairing**, not at init — the prospect's
phone number isn't known until they text the pool number.

## Opaque-token correlation

`POST /v1/trial/init` returns an opaque `token`. That's the only
handle your code gets to track the trial in your own systems. iSnap
stores no email, customer record, or business identifier on the trial
row.

The token is what your CRM keeps mapped to your customer. Status
queries (`GET /v1/trial/status?token=…`) and conversion calls
(`billing.checkout({ trial_token })`) both reference it.

## Webhook fan-out

The 4-event trial family fires to whichever account minted the trial:

- `trial.linked` — pairing succeeded; the prospect texted the pool
  number.
- `trial.dormant` — no message in either direction for
  `dormancy_window_hours` (default 24).
- `trial.reactivated` — a dormant trial got a new inbound.
- `trial.converted` — the trial was upgraded to a paid line.

Each payload includes `trial_id`, `token`, `pool_line_id`, and
`paired_handle`. No identity fields.

## Lifecycle

```
[no trial]
    │
    │ POST /v1/trial/init
    ▼
pairing_pending  ────────── (15 min) ──────────►  expired
    │
    │ prospect texts pool_line_number
    ▼
paired  ⇄ (24h no traffic) ⇄  dormant
    │           │
    │           └── inbound ──► reactivated ──► paired
    │
    │ billing.checkout({ trial_token })
    ▼
converted (terminal)
```

`expired` and `converted` are terminal states. The pool line slot frees
in both cases.

## Trials count toward usage

Each trial reserves a real shared-pool line and consumes real
device-side resources. Trials are tracked on your account's usage
ledger (visible in the dashboard) the same way regular sends are.
Conversion to a paid line carries the trial's billing context
forward — the `trial.converted` event is the audit trail.
