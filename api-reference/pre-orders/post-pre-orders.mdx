---
title: "Create a pre-order"
description: "Reserve a rental line in advance when the catalog is empty for your preferred area code."
openapi: "POST /v1/pre-orders"
---

Submits a pre-order for a rental line of the requested tier and area
code. iSnap fulfills it from the next available device once the
farm provisions one matching your preferences.

Use this when
[`GET /v1/lines`](/api-reference/lines/get-lines) returns no
available lines for the area code or tier you need. Pre-orders are
queued first-come, first-served per tier.

## Request shape

```json
{
  "billing_tier": "rental_iphone",
  "preferred_area_codes": ["415", "650"]
}
```

| Field | Value |
|---|---|
| `billing_tier` | Required. `rental_iphone` or `rental_android`. (BYOD doesn't pre-order — slots provision instantly via the dashboard at [platform.isnap.ai](https://platform.isnap.ai).) |
| `preferred_area_codes` | Optional. Up to 5 codes (3–10 chars each). iSnap matches the first available; falls back to any code if all 5 are exhausted. Empty array means "any area code". |

## Response

A `PreOrder` record with the initial state:

```json
{
  "id": "uuid-of-the-pre-order",
  "billing_tier": "rental_iphone",
  "preferred_area_codes": ["415", "650"],
  "status": "pending",
  "amount": 25000,
  "estimated_fulfillment": "2026-05-15T00:00:00Z",
  "fulfilled_line_id": null,
  "device_status": null,
  "created_at": "2026-05-11T22:00:00Z",
  "updated_at": "2026-05-11T22:00:00Z"
}
```

| Field | Notes |
|---|---|
| `status` | Lifecycle state — see below. |
| `amount` | Cents. The line's monthly price prepaid as a deposit; refunded if iSnap can't fulfill. |
| `estimated_fulfillment` | ISO timestamp iSnap commits to. Best-effort, surfaced for UX. |
| `fulfilled_line_id` | Set once the pre-order resolves to a real line. |
| `device_status` | Internal provisioning state for visibility — `awaiting_hardware`, `setup_in_progress`, etc. |

## Lifecycle

```
pending  ──► provisioning ──► ready ──► fulfilled
   │            │
   └── cancel ──┴── refunded
```

- `pending` — accepted, waiting for hardware to be allocated.
- `provisioning` — hardware allocated, iSnap operator is setting it
  up.
- `ready` — line is provisioned but the customer hasn't claimed it
  yet (rare; usually skipped to `fulfilled`).
- `fulfilled` — `fulfilled_line_id` is set, billing started.
- `cancelled` — caller called [`POST /v1/pre-orders/{id}/cancel`](/api-reference/pre-orders/post-pre-orders-id-cancel).
- `refunded` — terminal after cancel if the deposit was charged.

## When the deposit charges

The deposit captures at `provisioning` (when iSnap commits hardware
to the order). If you cancel before `provisioning`, no charge occurs.
After `provisioning`, cancellation triggers a refund.

## Errors

Universal codes (`401 invalid_api_key`, `500`, `503`) and the envelope
shape are documented in
[Conventions → Errors](/api-reference/introduction#errors).
Endpoint-specific codes:

| HTTP | `error.code` | Cause |
|---|---|---|
| 402 | `payment_method_required` | No payment method on file for the deposit. |
| 422 | `validation_error` | `billing_tier` not in the enum, or more than 5 area codes. |
