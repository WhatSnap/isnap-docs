---
title: "BYOD vs Rental"
description: "Which SKU fits your case, what events you receive, what iSnap shields you from."
---

iSnap ships three SKUs (`rental_iphone`, `rental_android`, `byod_imessage`,
`byod_android`) — or really, two postures: **rental** and **BYOD**. The
choice between them is about who owns the hardware and, downstream, who
sees the noise when something goes sideways.

## The headline trade-off

| | Rental | BYOD |
|---|---|---|
| Hardware ownership | iSnap | You |
| Monthly price | ~$175 (Android) / ~$250 (iMessage) | ~$15 / device |
| Setup time | iSnap operator picks a line off the shelf | 4-step bridge install |
| Failure recovery | iSnap ops handles it | You handle it |
| Health visibility | Durable events only | Full health surface |
| Best for | Hands-off integrators, scaling fast | Cost-sensitive, comfortable with hardware |

Both share one API, one billing relationship, one account. Mix freely.

## What iSnap shields rental from

On rental, you have **no access to the hardware**. Surfacing
transient state (`line.offline` for 30 seconds during a Mac restart,
`line.degraded` for missed heartbeats) creates alert noise with no
actionable resolution — you can't fix anything because the device
is in iSnap's farm.

So rental lines emit only **durable, actionable** events:

- `line.connected` — the line is live and able to send (fires on
  activation; for BYOD also on bridge re-connect after an outage).
- `line.apple_id_flagged` — Apple flagged the iMessage line (real
  problem, real recovery time, you should know).
- `line.quota_warning` / `line.quota_exceeded` — bucket fired.

`GET /v1/lines/{id}/health` returns `403 rental_health_not_exposed`
for rental tiers.

## What BYOD exposes

You own the hardware → you can act on issues → iSnap exposes the full
state machine:

- `line.connected` — bridge online (also fires on the initial pair
  completion).
- `line.disconnected` — bridge dropped its long-lived connection.
- `line.offline` — bridge has been unreachable past the offline
  threshold.
- `line.degraded` — bridge online but missing heartbeats.
- `line.apple_id_flagged` — same as rental, BUT the recovery path
  differs (you re-auth via the bridge).
- `line.quota_warning` / `line.quota_exceeded` — same as rental.
- `GET /v1/lines/{id}/health` returns the current state, last-seen-at,
  recent error history.

The model: same data, different projection. The data model
(`line_health` table, `device_sessions` heartbeats) is identical;
the API gates `/health` and the rental-suppressed events on
`line.byod === true`.

## What events you receive

| Event | Rental | BYOD |
|---|:---:|:---:|
| `line.connected` | ✓ | ✓ |
| `line.apple_id_flagged` | ✓ | ✓ |
| `line.quota_warning` | ✓ | ✓ |
| `line.quota_exceeded` | ✓ | ✓ |
| `line.disconnected` | ✗ | ✓ |
| `line.offline` | ✗ | ✓ |
| `line.degraded` | ✗ | ✓ |
| `message.received` | ✓ | ✓ |
| `message.sent` / `delivered` / `failed` | ✓ | ✓ |

A line spanning both surfaces (you have rental and BYOD lines on the
same account) gets the union of events scoped per `line_id`. Branch on
`event.data.line.byod` if your handler differs.

## Mixing tiers

There's no penalty for mixing. Common patterns:

- **Rental for production, BYOD for dev.** Rental lines for live
  traffic; a BYOD Mac in the office paired to a test API key for
  integration work.
- **BYOD for some accounts, rental for the rest.** Mix freely across
  the same iSnap account.
- **Trial → BYOD → rental.** Start on a trial, move to BYOD (low
  monthly), upgrade to rental once volume justifies handing off the
  hardware management.

Billing aggregates across tiers — one account, one invoice.

## When to switch from BYOD to rental

Triggers to consider rental over BYOD:

- You're saturating the BYOD line's daily warming-stage cap
  consistently — rental tiers run with more headroom and a managed
  warming pool.
- You're spending real time troubleshooting offline state on your Mac
  — hardware reliability is no longer the right abstraction.
- Your BYOD line keeps catching Apple flags despite clean sending
  patterns — iSnap's managed Apple ID pool has more rotation options
  than a single self-owned ID.

The migration is: release the BYOD line, assign a rental line, and
re-attach any downstream identity (e.g. the recipient list in your own
system). The underlying phone number changes, so conversation history
keyed by number doesn't auto-carry over.
