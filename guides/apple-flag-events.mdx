---
title: "Handling Apple flag events"
description: "What line.apple_id_flagged means, how to recover, what to tell the end-user."
---

iMessage delivery depends on Apple keeping the line's Apple ID in good
standing. If Apple flags the account — usually for sending patterns it
considers suspicious — iMessage stops working immediately. iSnap fires
a `line.apple_id_flagged` webhook so you can react fast.

Recovery differs depending on whether the line is **rental** or
**BYOD** — both cases below.

## What triggers a flag

Apple doesn't publish its rules, but the patterns most likely to flag
a line are:

- **Sending shapes that look automated** — bursts, regular cadence,
  identical bodies across many recipients.
- **Low reply rate.** This is the most reliable signal. The
  [warming model](/concepts/quotas-and-warming) and the new-vs-known
  contact split exist to keep this ratio healthy.
- **Aggressive opt-out reports** — recipients tapping "Report Junk"
  enough times.

Once flagged, iMessage sends from the line start failing. The line
itself is still alive — SMS and RCS keep working. Only iMessage breaks.

## The webhook

```json
{
  "id": "evt_01HX...",
  "type": "line.apple_id_flagged",
  "api_version": "1.0.0",
  "created_at": "2026-05-05T14:32:00Z",
  "data": {
    "line": {
      "id": "line_aBc...",
      "billing_tier": "rental_iphone",
      "byod": false,
      "phone_number": "+15559998888"
    },
    "detected_at": "2026-05-05T14:31:55Z"
  }
}
```

This event fires for **both rental and BYOD** lines — Apple flags are
durable and actionable (pricing tier doesn't matter), so they're
not in the rental-suppression list.

## Recovery

### Rental lines

iSnap ops handles the recovery. v1 doesn't ship a dedicated
"recovered" event yet — poll the line's
[`GET /v1/lines/{id}/health`](/api-reference/lines/get-lines-id-health)
(BYOD) or check the next `line.connected` / outbound success
to confirm iMessage is back.

While the line is flagged, route iMessage traffic away from it (your
fallback chain) or pause outbound on that line. Don't keep retrying —
Apple will hold the flag longer if traffic keeps coming.

Typical recovery time: **2–24 hours**. Severe cases (multiple flags
in a week) may require Apple ID rotation, which iSnap operators handle.

### BYOD lines

You own the Apple ID, so you'll need to re-auth via the bridge:

1. The flag surfaces in your dashboard / via the webhook with clear copy:
   *"iMessage on +1 555… is temporarily unavailable. Re-auth your Apple
   ID via the bridge to restore it."*
2. Open the bridge — it presents Apple's re-auth flow (web view → 2FA
   on the trusted device).
3. Once re-auth succeeds, the bridge resumes sending. Confirm by
   sending a test iMessage or by checking
   [`GET /v1/lines/{id}/health`](/api-reference/lines/get-lines-id-health)
   — the health snapshot clears the Apple flag once the bridge
   reports success.

## Communicating downstream

If you re-expose this signal in your own product, three things matter:

1. **What's broken.** "iMessage is temporarily unavailable for this
   line." Avoid "your account is flagged" — it reads like a moral
   judgment. It's not.
2. **What still works.** SMS and RCS keep going. If your fallback
   chain handles the swap automatically, lead with that.
3. **What action is needed.** For BYOD, link the bridge re-auth flow.
   For rental, "iSnap is on it; expected back within 24h" is honest.

## Suppress the alert noise

Don't panic-page on every `line.apple_id_flagged`.
Production-grade integrations:

- **Group by line.** A single flag doesn't deserve 15 escalations.
- **Suppress within a 24h window** — once notified, second + third
  flags on the same line in the same window get folded.
- **Surface persistent flags** (>72h without recovery) as ops
  escalation, not first-flag noise.

## Prevention beats recovery

The warming model and the 5-bucket quota gate exist to make flags
rare. If you see a flag, audit:

- Was the line warmed? See `GET /v1/lines/{id}/config`'s `warming_state`.
- Was the new/known contact ratio out of whack? Reply rate &lt; 30% is a
  red flag.
- Was traffic bursty? The hourly red-zone aggregator
  (`bucket: hourly_chronic`) flags this before Apple does.

[Concepts → Quotas + warming](/concepts/quotas-and-warming) covers
the prevention side end-to-end.
